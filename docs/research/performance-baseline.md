# 性能基线与验收方案

状态：调查和候选方案，数值门槛待确认。日期：2026-10-17。

本次已在本机对 Boost.Regex 1.89.0 做了九类小规模性能测量，保存了可复现程序、原始 CSV 和环境信息。Rust 引擎尚未实现，因此没有 Rust/Boost 性能比值。本次结果用于设计基准与发现测量问题；不能直接作为六个平台的发布验收结果。

## 基准来源与可复现材料

- [C++ 基准程序](assets/performance/boost-bench.cpp)：匹配编译、搜索、捕获、前瞻与反向引用、受限回溯失败、替换。
- [PowerShell 7 构建运行脚本](assets/performance/run.ps1)：仅使用已安装 MSVC，构建产物和日志默认写入 `target/research/benchmark/`。
- [原始结果](assets/performance/windows-x64-msvc.csv)，[环境及 SHA-256](assets/performance/windows-x64-msvc-environment.json)。

在仓库根目录执行：

```powershell
pwsh -NoProfile -File docs/research/assets/performance/run.ps1 -BoostRoot 'D:\NewProgram\librime-rs\target\regex-oracle-cache\boost_1_89_0'
```

本地参考源码目录为 `D:/NewProgram/librime-rs/target/regex-oracle-cache/boost_1_89_0`，版本头和编译时断言均确认 `BOOST_VERSION == 108900`；没有使用消费者 `third_party` 中带补丁的副本。已记录五个关键头文件的 SHA-256，但没有重新核验整个下载归档的官方校验和，故本报告将其称为“官方源码本地缓存基准”，不声称完成了整个缓存的来源认证。

上游 [timer 示例](https://www.boost.org/doc/libs/1_89_0/libs/regex/example/timer/regex_timer.cpp) 同样先缓存加载，再循环测量搜索；本次程序据此将表达式和输入准备、进程启动、构建及输出 CSV 排除在匹配计时之外。[搜索接口](https://www.boost.org/doc/libs/1_89_0/libs/regex/doc/html/boost_regex/ref/regex_search.html) 与 [替换接口](https://www.boost.org/doc/libs/1_89_0/libs/regex/doc/html/boost_regex/ref/regex_replace.html) 是测量操作的行为来源。

## 本地实测

| 条件 | 实测环境 |
|---|---|
| 系统 | Windows 11 Enterprise 10.0.26200，x86-64 |
| CPU | Intel Core i9-13900H，14 核、20 逻辑处理器 |
| 系统可见物理内存 | 68,314,955,776 字节 |
| 编译器 | 已安装 VS 18 Enterprise MSVC 19.51.36260.0，`_MSC_VER=1951` |
| 优化 | `/O2 /Ob2 /DNDEBUG /EHsc /std:c++17 /DBOOST_REGEX_NO_LIB /utf-8 /W4` |
| 字符规则 | `boost::regex` 的默认平台字符规则；未使用 ICU |
| CRT | 对象文件指令确认 `MT_StaticRelease`，`LIBCMT`/`libcpmt` 静态 release CRT |
| 线程 | 单线程调用；未固定 CPU 亲和性与电源策略 |

每项先独立检查预期结果，预热 100 次；倍增循环次数，直到一个校准批次至少 250 ms，再测量九批。操作内累计返回值，并检查每批 checksum；捕获和替换另有精确内容预检。编译项包含表达式构造及析构；匹配项复用已编译表达式；捕获项包含结果对象的创建和捕获位置/长度读取；替换项包含结果分配与释放。没有把 I/O 或进程启动时间除以操作数。

现有 CSV 是程序直接输出的九批汇总（中位数、最慢批均值、checksum），未保存每个批次的独立计时，因此不能用它补算原始批次置信区间。下述发布测量协议要求保存全部批次。

这是完整 Boost 配置的默认 Windows/Win32 traits 路径，未显式传入 `BOOST_REGEX_STANDALONE`、`BOOST_HAS_THREADS` 或 locale 切换宏；完整 Boost 配置仍可能根据编译器条件自动推导线程宏。消费者的 standalone、补丁、显式宏及 `/MD` 等配置不应被假定等同本次测量。对象文件的 `dumpbin /directives` 确认本次使用静态 CRT，而不是消费者可能使用的动态 CRT；后续同机比较必须固定这些配置及分配器差异，必要时另建消费者配置参考组。

墙钟采用 `std::chrono::steady_clock`；进程 CPU 时间采用 Windows `GetProcessTimes` 的用户态与内核态之和。CPU 列来自独立读数，不是墙钟时间的另一个名称。[Microsoft 对 GetProcessTimes 的定义](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes) 也明确其为进程累计 CPU 时间。受计时分辨率、调度与取样边界影响，两列不必相等，不宜把这里的 CPU 数值解读为精确到纳秒的性能。

以下时间均为每次操作的微秒数；“最慢批均值”是九批中的最大均值，不是单次延迟 p95。

| 工作负载 | 输入规模 | 墙钟中位数 µs | 最慢批均值 µs | CPU 中位数 µs |
|---|---:|---:|---:|---:|
| 编译普通捕获表达式 | 表达式 33 字节 | 3.048 | 3.274 | 2.899 |
| 编译前瞻与反向引用 | 表达式 25 字节 | 1.641 | 1.772 | 1.602 |
| 普通搜索命中 | 29 字节 | 0.274 | 0.292 | 0.277 |
| 搜索并读取捕获 | 29 字节 | 0.294 | 0.326 | 0.286 |
| 大文本搜索未命中 | 1 MiB | 320.815 | 405.340 | 312.500 |
| 前瞻与反向引用匹配 | 25 字节 | 0.146 | 0.169 | 0.143 |
| 受限回溯未命中 | 18 个 `a` 后跟 `b` | 254.197 | 259.146 | 253.906 |
| 短文本全局替换 | 17 字节 | 0.543 | 0.549 | 0.553 |
| 大文本全局替换 | 256 KiB，32,768 次匹配 | 6,020.609 | 6,925.495 | 5,937.500 |

普通表达式为 `([A-Za-z_][A-Za-z_0-9]*)=([0-9]+)`；复杂匹配为 `^(?=.{1,64}$)([a-z]+)-\1$`；受限回溯为 `^(a|aa)+$`。回溯输入固定为 19 字节，避免把指数增长输入扩展成不受控的长任务。大替换将每行 `alpha=12 beta=3\n` 变为 `12:alpha 3:beta\n`，结果大小相同。

本次属于共享开发机上的试测，Intel 混合核心、调频及并发负载均可能影响结果。先前 50 ms 校准的探索性运行中，普通编译约 2.06 µs，而最终运行约 3.05 µs，表明跨运行漂移足以影响性能判断；最终 CSV 只保留统一 250 ms 协议结果。不能据单次数字规定所有机器上的绝对纳秒指标。

## 候选门槛

以下是建议预算，不是由尚不存在的 Rust 实测推导出的结论，也尚未成为已接受决策。每一工作负载和每一承诺目标分别验收，不能用整体平均值抵消某项退化。

| 项目 | 首版候选门槛，Rust / 同机 Boost |
|---|---|
| 普通搜索、捕获、迭代、替换 | 操作耗时中位数 ≤ 1.5 倍 |
| 编译、复杂语法、受限高回溯、Unicode 与 locale | 操作耗时中位数 ≤ 2.0 倍 |
| 编译结果持有内存、执行峰值工作内存 | 各自 ≤ Boost 的 2.0 倍 + 64 KiB |
| 结果输出占用 | 另列逻辑结果字节数及实际分配容量；完整操作的峰值分配 ≤ Boost 的 2.0 倍 + 256 KiB |

1.5 倍为普通调用提供明确的迁移性能预算；复杂能力和编译允许 2 倍，为首版实现保留空间。这是工程取舍，需要用户确认，不能声称这些数值已由上游保证。内存固定余量用于避免小输入中很小的 Boost 分母放大比值；对大输入仍由比例约束增长。内存项目之间有重叠，应分别报告，不能将余量逐项相加来放宽整个操作。

耗时主门槛采用与同机 Boost 交错运行所得的墙钟操作均值之中位数；CPU 时间作为独立辅助指标，出现明显背离时先检查调度与计时方式。不会将本表的 Windows 墙钟数字直接用作 Linux、macOS 的绝对阈值，也不会把跨语言不同工作量的 API 调用拿来计算比值。

本次**没有测量内存**。上述内存数值仅是候选预算；不能将主机物理内存、进程工作集或文本大小当作引擎工作内存。实施验收时应区分已编译结果的常驻分配、执行临时峰值、输出分配、总操作峰值，并记录分配器测量的覆盖范围。进程私有提交或 RSS 仅作旁证，跨平台值分开解释。

## 完整验收的测量协议

1. 保留本次九项作为基准骨架；补充 POSIX 选择、全部捕获、零宽迭代、失败路径、大型表达式、UTF-16/32、ICU 分类与排序、约定 locale、自定义字符规则。输入长度、命中位置、命中密度、语法和选项写进版本化数据集。消费者现有 91 个语义样例用于正确性回归，本身不代表完整性能覆盖。
2. Rust 使用优化构建，C++ 使用对应优化构建；记录 rustc、C++、链接器、标准库、分配器、系统、locale、ICU、数据版本、源码 hash。共享相同输入、结果请求和生命周期，普通匹配复用编译结果；冷启动与编译另测。首次接触分配器/数据加载的成本单独报告。
3. 两边先通过同一语义对照，再计时；校验匹配范围、全部捕获及替换输出。基准循环内保留可观察 checksum，防止结果被优化掉；预检的内容扫描成本不混入匹配操作。
4. 发布测量采用空闲且电源稳定的同一台机器，记录亲和性与核心类型；Boost/Rust 交错顺序，每项至少 30 个有效批次，批次至少 250 ms。记录原始批次、噪声和置信区间；差异落在噪声区间时结果为待定，排除环境因素再测，不能自动提高门槛。
5. 内存使用单独的分配追踪运行，避免把追踪开销加入速度成绩。排除数据集预加载与调用者输入，分别标记引擎与输出；编译结果构造完测持有分配，再记录执行峰值。分配钩子无法覆盖的平台 API 分配必须说明，并以进程级指标补充。
6. Windows/Linux/macOS 的 x86-64、ARM64 都运行语义和性能套件。共享 CI 可用于回归提示，发布门槛在可重复的机器环境执行；缺少某目标的测量时，该目标保留为未验收。

需要后续实施才能得到的事实包括六目标的真实 Rust 比值、ICU/Unicode 耗时、原生 locale 调用开销、全部内存指标。当前可直接确定的是数据集与测量协议；候选倍率及固定内存余量仍待确认。
