# 剩余事项的具体方案

调查日期：2026-10-17。本文保留研究提案及证据。**Q27 已确认字符数据版本、六目标系统验证基线、耗时 1.5/2 倍与工作内存 2 倍加 64 KiB 门槛，并授权优先验证字符规则和排序键**，现已写入 ADR-0002/0003。自动测试执行时长等未被逐项确认的建议仍为提案；本文不是已完成全部验收的报告。

## 已完成的调查与测量

- 已读取用户提供的 Boost 1.89.0 本地源码、官方文档和测试目录；未修改参考源码或 `librime-rs`。
- 已核对 ICU / Unicode / CLDR 官方发行资料与 ICU4X 对应源码，并运行独立探针：1,114,112 个码点的九字段适配对照零差异；初轮 5,290 对有效排序比较一致，230 对因参考空串异常未判定。补充非 FCD 语料发现 145 对实际排序差异，否证直接采用 ICU4X 默认排序路径；完整键及名称尚未通过 Rust 对照，详见 [ICU 探针实测](icu-probe-results.md)。
- 已核对六目标的官方 runner 与平台资料。仓库公开且 Actions 已启用，但未触发任何远程作业；六目标完整验收尚未执行。
- 已在本机 Windows x64 对 Boost 进行九项小规模编译、搜索、捕获、复杂语法和替换测量，保留脚本、结果与环境。Rust 引擎尚未实现，因此没有 Rust 性能比值、内存达标或跨平台达标结论。

## 1. 字符与 locale 基准

建议固定 **Boost.Regex 1.89.0 + ICU4C 77.1 + Unicode 16.0.0 + CLDR 47**。使用原版完整 ICU 数据，保存发布 tag 对应 commit、库与数据摘要；不使用环境中任意版本的 ICU。Rust 工具链继续跟随 stable，字符语义数据不随 Rust 标准库更新而漂移。

理由：该组合有明确的官方发行依据；ICU4X 2.0 的编译数据版本也对应 Unicode16 / CLDR47，适合做首轮候选验证。**同版数据不保证相同行为。** ICU4X2.0 不提供完整 sort-key 输出入口；Boost 公开的 `transform` / `transform_primary` 返回值不能只凭排序顺序一致就判通过。字符名称反查、extended 名称等也需单独实现或验证。

建议先做不依赖正则引擎的 traits 对照探针：逐码点大小写/类别/数字、名称查找、PRIMARY/IDENTICAL 排序键、locale 回退和别名。排序和数据缺口保留在首版完整验收中，不通过链接 C/C++ ICU、缩减 locale 或放宽结果等价性绕过。

这不是承诺复刻整个 ICU：范围是 Boost1.89 实际公开使用的 ICU 能力。完整能力清单必须精确对应其固定属性别名表，而不是额外开放 ICU 的全部属性语法。

详见 [ICU 基准与可行性调查](icu-baseline.md)，包含官方来源、源码定位及具体探针清单。

## 2. 六目标验收环境

| 目标 | 建议验证环境 | 原生 runner 候选 |
|---|---|---|
| Windows x86-64 MSVC | Windows Server 2025；本地 Windows11 测量作为补充 | `windows-2025` |
| Windows ARM64 MSVC | Windows 11 ARM64 | `windows-11-arm` |
| Linux x86-64 GNU | Ubuntu 24.04 LTS / glibc | `ubuntu-24.04` |
| Linux ARM64 GNU | Ubuntu 24.04 LTS / glibc | `ubuntu-24.04-arm` |
| macOS x86-64 | macOS 15 Intel | `macos-15-intel` |
| macOS ARM64 | macOS 15 Apple Silicon | `macos-15` |

这些是可执行的验证基线提案，不是对全部旧系统版本的运行承诺。一轮验收固定同一个实际 stable 版本与语料；记录镜像、OS、CRT/libc、locale 数据、编译器和参考程序身份。标签内容可能更新，因此不能只保存 runner 名称。

locale 快速回归集合：各后端自己的 C / classic / invariant / root，加 en、tr、de、ja、zh、sv；ICU 排序另外覆盖 fr_CA、传统西班牙语、泰语等。C、invariant 与 root 不相互替代。Win32、C、C++ 和 ICU traits 分开对照；Windows 窄字节加入 CP1252/1254/932/936 与 UTF-8 环境。

这些是定向测试集，**不是产品只支持这些 locale**。ICU 完整数据的可用 locale / collation 类型另行枚举验证；系统后端依据实际可用名称和上游行为记录结果，缺少环境不能静默跳过并算通过。

详见 [平台与 locale 矩阵](platform-matrix.md)。目前已确认仓库为 PUBLIC、Actions enabled；实际原生调度和六目标测试仍未验证。

## 3. 分项性能门槛提案

首版性能门槛建议以下列候选值进入后续验证设计。数值是产品取舍建议，**不是测量证明 Rust 已能达到的结果**：

| 项目 | 候选门槛 |
|---|---|
| 普通搜索、捕获、替换 | 每项耗时不超过同环境 Boost 的 1.5 倍 |
| 编译、复杂语法、Unicode | 每项耗时不超过同环境 Boost 的 2 倍 |
| 引擎工作内存 | 候选为 Boost 对应工作内存的 2 倍加 64 KiB；需先实现双方一致的计量 |
| 结果内容 | 正确性必须先通过，不能靠减少捕获或输出换取性能过线 |

含复杂语法或 Unicode 的捕获/替换采用其专项类别；套件预先固定分类，不能在结果不佳后重新归类。各项独立验收，不通过整体平均分抵消退化。

一次性结果与引擎工作内存分开统计；尚未测量的内存不能用进程总内存或输出文本大小代替。性能比较在同一原生环境交替运行两个实现；保存完整批次数据与结果校验。发现明显机器噪声或跨进程漂移时先复测，不能据此放宽产品门槛。

本轮 Boost 测量只是确定量级和验证方法的起点：不含 ICU，未测工作内存，也没有完成六目标覆盖。正式套件仍需覆盖语法/选项/编码/输入规模矩阵。实测值、配置及复现方法详见 [性能基线](performance-baseline.md)。

## 4. 新增预算与测试投入

建议额外预算配置采用“未配置即不启用”，不增加默认上限或通用生产预设。需要控制的调用者给出工作量、引擎工作内存、输出字节数或匹配数上限。编译预算独立；一次替换或一个迭代器遍历中的执行预算累计，不在每次找到匹配后重置。该累计规则属于待确认扩展，不改变默认语义。

超限结果处理已经确认并写入 ADR-0003：完整结果报错；迭代保留已交付项，报错一次后结束；外部输出保留已写内容并报错，不回滚。

建议测试投入：每 PR 六目标确定性测试，并在 Windows/Linux x64 各做 5 分钟生成测试；每夜四类目标各 30 分钟；发布候选四类各累计 6 CPU 小时，所有反例在六目标重放。这些是起始预算建议，未创建 CI 或定时任务，也不等于测试覆盖证明。

原版 Boost 的状态限制不是简单的固定一亿步。精确源码依据、资源计量边界、预算边界测试及上游能力清单组织见 [资源与验证方案](resource-and-validation-proposal.md)。

## 5. 建议推进顺序

1. **参考环境与清单**：确认上述版本/矩阵/门槛候选；下载时验证来源与摘要，建立原版参考、消费者修补参考和逐能力清单。先验证六目标参考程序可运行。
2. **字符规则探针**：优先验证最可能影响整体设计的 ICU 排序键、名称与平台 locale 行为，再决定最终 Rust 数据与依赖实现方式；不因缺口改变完整交付要求。
3. **性能与预算契约**：扩充基准语料，确定统一内存计量、工作量定义、必要引擎限制与外部预算边界。冻结具体验收条件后进行正式性能比较。
4. **主体实现与完整验收**：分步实现公开能力，但只有完整清单和约定测试全部满足才算首版交付；`librime-rs` 接入继续暂缓。

以上是工程阶段提案，步骤1–3的研究验证不等于开始实现正式引擎，也不等于降低首版要求。已完成报告、小规模 Boost 基线以及 ICU 独立探针；后续完整键和名称原型的具体方案见 [实测报告](icu-probe-results.md)。

## 需要单独处置的上游行为

- `icu_regex_traits::getloc()` 返回默认 locale、内部 `imbue` 保存请求 locale 的行为已实测复现；Q28 已确认保留。
- 空串 IDENTICAL 排序在当前 Boost + ICU 77.1 组合下访问异常；Q29 已确认 Rust 返回有效排序键并记录兼容例外。以上两项见 [ADR-0005](../adr/0005-icu-locale-query-and-empty-sort-key.md)，并不表示 Rust 实现已经完成。
- 使用方的 Windows ANSI 分类初始化补丁需要和原版分别执行对照。对于不稳定或未定义结果，不以一次原版运行结果当固定契约；提出确定行为及差异记录后再决定。

Windows ANSI 补丁差异仍需实际对照；其它具体差异继续执行既定的逐项决策规则。
