## Outcome and reason

The C-locale backend has global-locale and character-unit semantics distinct from C++ and ICU traits.

## Starting state

The cloud reference currently uses cpp_regex_traits<char> with classic C only.

Published source baseline: `1b0149efb649bcec7b5d6c4c0be2f7e403189cea`. Paused implementation sources are preserved separately in the [checkpoint](https://github.com/1298345095/BoostRegexRS/blob/work/root-primary-cloud/docs/development/tickets/checkpoint/README.md). Restore them in an isolated checkout when resuming; an archive is not validation evidence.

## Deliverable

- Build a separately identified c_regex_traits byte/wide oracle and implement its classification, mapping, numeric, name and full transform behavior using pure Rust plus permitted system APIs.
- Wire the backend into compilation and matching; isolate tests that change process-global locale.

## Acceptance

- [ ] An end-to-end locale matrix compares trait returns, full transform keys, range/equivalence matching, captures and errors against Boost C traits.
- [ ] Every requested locale creation failure is recorded as reference-unavailable, implementation-error or unsupported-name with evidence.
- [ ] Runtime dependencies contain no C++/ICU library; actual glibc and locale data identity are recorded.
