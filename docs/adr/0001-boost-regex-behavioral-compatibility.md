# 以 Rust 重实现 Boost.Regex 的行为

用户已有一个通过 C ABI 调用 Boost.Regex 的 Rust 程序，希望让该程序直接使用 Rust 实现；同时希望为其他使用者提供兼容库。因此选择以纯 Rust 行为兼容重实现为方向，内部设计可以调整，不要求复刻上游源码结构，也不以继续封装 C++ Boost.Regex 作为最终实现。

最终目标是全面兼容 Boost.Regex，而非永久限定为功能子集。首个可交付版本需要完整能力达到约定的验收标准，不以现有封装层使用的功能子集作为首版完成标准。开发过程可以分步实现，但分步实现不改变交付门槛。

当前交付范围是本仓库的独立 Rust 库、公开文档及完整兼容和性能验收。实际替换 `librime-rs` 的工作暂缓，不属于当前交付范围；若后续恢复接入，仍须以本库完整验收通过为前提。

以官方 Boost.Regex 1.89.0 为主兼容基准，同时验证现有程序使用的修补版本。现有调用方位于 `D:/NewProgram/librime-rs/crates/boost-regex-sys`，用于调查使用条件，不用于缩小完整移植的范围。

当上游实际行为与文档或预期冲突时，逐项决定是否保留，并记录兼容差异及迁移方式。尚不预设所有上游怪癖必须复制，也不预设一律按文档纠正。

消费者随附源码的 README 记录了一处 Windows ANSI 字符分类表初始化补丁。官方上游与消费者修补版本分别标识，补丁造成的行为差异按上述规则逐项决定。

完整能力包括全部语法、匹配、捕获、替换、迭代、选项，以及字节、宽字符、Unicode、locale 和自定义字符规则的扩展能力。提供 Rust 等价接口，不要求原样复制 C++ 类名、模板写法或 ABI。字符和平台约束见 [ADR-0002](0002-native-dependencies-and-platform-semantics.md)。

普通安装默认提供全部能力，包括 Unicode、宽字符和 locale。后续可以支持显式关闭可选模块以减少依赖和体积；默认配置及完整配置均须有对应测试，不能因功能开关遗漏兼容能力。

错误兼容要求相同的错误类别与位置，不要求消息文本逐字一致。资源限制引起的接受或拒绝差异遵循 [ADR-0003](0003-resource-contract-and-release-acceptance.md)，不要求复现上游内部限制的触发点。

Rust API 采用完整、安全的原生接口，现有程序的适配暂缓；输入与位置约定见 [ADR-0004](0004-rust-api-and-input-positions.md)。具体系统与字符数据版本、资源预算数值及具体差异处理仍待后续调查和决策确定。
