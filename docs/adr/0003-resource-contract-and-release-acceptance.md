# 独立资源契约与完整交付验收

为了允许内部重新设计，BoostRegexRS 使用自身可配置的资源限制，达到限制时返回明确错误，不承诺复现 Boost 的限制或触发条件。如果 Boost 因资源限制而失败，而本库能在自身预算内完成，则允许返回成功结果。这是行为兼容的明确边界；未触及资源限制的匹配结果仍须符合兼容契约。

默认调用以 Boost 行为兼容为目标，不额外强加输出大小上限、整次遍历累计预算等新限制。这些新增预算作为扩展能力，由调用者显式配置启用，普通调用不必传入预算参数。不开启新增预算不等于取消引擎自身必要的资源限制。

启用新增预算后，超限必须报告明确错误，不能伪装成未匹配，也不能返回貌似成功的截断结果。一次性返回完整结果的接口返回错误，不以截断内容冒充完整结果；逐项迭代保留已返回的匹配，超限时报告一次错误后结束；写入调用者提供的输出目标时，保留已写出的内容并返回错误，不承诺撤销写入。具体预算数值和累计计量方式仍需细化。

首版性能是交付门槛，覆盖编译、匹配、替换耗时及内存占用。已确认普通搜索、捕获、替换每项耗时不超过同环境 Boost 的 1.5 倍；编译、复杂语法和 Unicode 每项不超过 2 倍；引擎工作内存不超过 Boost 对应工作内存的 2 倍加 64 KiB。复杂语法或 Unicode 的捕获/替换进入预先固定的专项类别，不能在结果不佳后重新归类。

这些是验收上限，不是已有性能结论。正式比较需要相同输入、结果请求和生命周期，以及同环境交错运行的有效批次；内存需建立双方一致的计量。尚未实现 Rust 引擎或完成内存测量时不能宣称达标。研究报告中的完整操作峰值分配等其他数值不因本次确认而自动成为新增门槛。

性能按工作负载分项验收，分别覆盖编译、普通搜索、捕获、复杂语法、替换和 Unicode，并区分短文本、大文本及高回溯输入。每类检查耗时和内存，不以整体平均分代替分项门槛。阈值根据 Boost 基线测量提出，经用户确认后，不因实现未达标而自动放宽。

完整交付采用以下验收要求：

1. 将上游公开能力逐项列成清单，每项都有实现和对应测试。
2. 移植适用的上游测试，并与固定版本的 Boost 进行结果对照。
3. 对照匹配范围、所有捕获、替换输出、错误，以及字符规则和选项组合。
4. 在 Windows、Linux、macOS 的约定环境中运行测试，并补充自动生成用例和模糊测试。
5. 所有已知差异必须修复，或由用户明确接受并记录；不能留下未处理的已知差异。
6. 现有程序的语料作为补充回归测试；实际接入暂缓，不属于当前交付范围。后续若恢复接入，仍在完整验收之后。

资源预算、详细测试矩阵以及自动生成用例和模糊测试的执行预算待后续确定；性能阈值已经确认，测量协议及套件仍需落实。
